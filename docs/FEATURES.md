## 1. Project goal

> Nobody in Thailand publishes the rail network as a structured, versioned,
> temporally-aware open dataset. The map is how we prove the dataset is good.

- **The dataset is the product.** The web map is a reference implementation.
  If a change helps the map but hurts the dataset, the dataset wins.
- **Coverage:** Bangkok plus Nonthaburi, Samut Prakan and Pathum Thani. Do not
  assume the network fits inside Bangkok province.
- **Time-aware:** every station and segment carries validity windows, so the
  network can be shown as it was in any year.
- **Provenance:** every fact carries `source_refs`. A change without a source
  is rejected.
- **Public good:** open licences (code AGPL-3.0, data ODbL-1.0), no commercial
  intent, near-zero hosting cost.

### Non-goals

Real-time train positions, a production journey planner, ticketing, native
apps, anonymous crowd editing, monetisation. See SPEC.md section 5 for the
reasons. A reference route planner that demonstrates the graph is an idea
(SPEC 5.7), not a non-goal.

## 2. Current phase

**Phase 1: public read-only site** (public beta), plus parts of Phase 2 (time
travel).

- `apps/web` is a Next.js static export, deployed on Vercel.
- No database, no API, no admin panel yet. The site reads a committed
  `network.json` built from `data/source/`. The one exception is an optional
  view counter in an isolated stats store ([ADR 0002](adr/0002-visit-counter.md));
  the map works without it.
- The schema is already bitemporal and revision-shaped, so the Phase 3 admin
  plane can be added without a migration.

## 3. Dataset

### 3.1 Coverage

| Entity   | Count | Source of truth               |
| -------- | ----- | ----------------------------- |
| Lines    | 10    | `data/source/lines/*.json`    |
| Stations | 192   | `data/source/stations/*.json` |
| Segments | 187   | `data/source/segments/*.json` |

Lines: Airport Rail Link, BTS Sukhumvit, BTS Silom, BTS Gold, MRT Blue,
MRT Purple, MRT Pink, MRT Yellow, SRT Dark Red, SRT Light Red.

Counts are from the build at the date above. Regenerate with
`bun run data:build` and check `data/dist/network.json` for current numbers.

### 3.2 Published artifacts

Generated by `bun run data:build` into `data/dist/`, then copied into the site
and offered on `/download`.

| File              | Contents                                             |
| ----------------- | ---------------------------------------------------- |
| `network.json`    | Current-state lines, stations, segments (no history) |
| `network.geojson` | Station points and segment lines for GIS tools       |
| `stations.csv`    | Flat station table for spreadsheets                  |

### 3.3 Data guarantees (enforced in CI)

| Guarantee                                          | Where                                           |
| -------------------------------------------------- | ----------------------------------------------- |
| Every entity matches the JSON Schema               | `packages/schema`, `data:validate`              |
| No orphan stations or dangling segments            | `packages/network-graph`, `data:validate`       |
| Interchange groups resolve                         | `scripts/build/interchange-groups.test.ts`      |
| Every mutation has non-empty `source_refs`         | `scripts/validate/check-source-refs.ts`         |
| `status` is derived from milestones, never edited  | `scripts/build/assemble.ts`                     |
| Generated JSON Schemas are committed and current   | CI `git diff --exit-code`                       |
| Performance budgets (bundle, payload)              | `check-bundle-size`, `data:validate`            |
| `last_verified_at` is never in the future          | `scripts/validate/check-verified-dates.ts`      |
| Changed entities bump `last_verified_at` (warning) | `scripts/validate/check-verification-bumped.ts` |

### 3.4 Data workflow

| Step                 | Command / location                                    |
| -------------------- | ----------------------------------------------------- |
| Import raw OSM       | `bun run data:import` (writes `data/source/osm-raw*`) |
| Seed historical eras | `bun run data:seed` (runs seeds in dependency order)  |
| Manual corrections   | `data/overrides/*.json`, reviewed via PR              |
| Build artifacts      | `bun run data:build`                                  |
| Validate             | `bun run data:validate`                               |

`data/source/` is write-once. Corrections go in `data/overrides/`. Data
changes use the `data:` commit type and are never mixed with code changes.

## 5. Engineering features

| Area             | What exists                                                                                                            |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Monorepo         | Bun workspaces: `packages/{schema,geo-utils,network-graph,renderer,ui}`, `apps/web`, `scripts/{import,build,validate}` |
| Single schema    | Zod in `packages/schema` generates TS types and JSON Schema. Never redefine an entity shape elsewhere                  |
| Temporal queries | `packages/network-graph/src/temporal.ts`, `apps/web/lib/asOf.ts` (tested)                                              |
| Geo utilities    | Reprojection between Indian 1975 / UTM 47N (THAI-W75) and WGS84, polyline tools, validators (tested)                   |
| CI               | Prettier, typecheck, Vitest, schema drift, data build, data validate, web build, bundle budget                         |
| Hosting          | Static export on Vercel, no env vars needed, portable to any static host                                               |

## 7. Notes for AI agents

1. Read `CLAUDE.md` before writing code. Its rules are decisions, not
   suggestions: data-first (never SVG-first), bitemporal, append-only
   revisions, static public plane, no history in the main payload, and no
   copying of copyrighted transit maps.
2. Station **ID** and station **code** are different and diverge over time.
   Use `code_history[]` for codes.
3. Never edit `status`; it is derived from `milestones[]`.
4. Never hardcode the deployment domain. Use relative URLs or
   `PUBLIC_BASE_URL`.
5. Keep within the performance budget (CLAUDE.md section 7). CI fails the
   build if you exceed it.
6. When you ship a user-visible feature, add or update its row in section 4
   of this file in the same PR.
